Reference Blueprint

Twilio LiveKit Call Handoff

A production-shaped pattern for giving a LiveKit voice agent a clean escape hatch back to Twilio routing, without losing the live caller, the context gathered by the AI, or optional Twilio Conversation Memory context.

View Call Flow Implementation Map Open GitHub Repo
Patterns: Studio, TaskRouter, custom TwiML, optional Memory Voice + LiveKit + routing

What This Blueprint Solves

AI containment with a safe parent-call handoff

The integration lets a LiveKit voice agent handle the first part of an inbound support call. When the agent cannot resolve the issue, it calls a tool that updates the original Twilio call. Flex is the tested reference destination, but the same pattern can route the live caller through Studio, TaskRouter, a voice app, SIP endpoint, conference, or dial target. The same architecture can also carry Twilio Conversation Memory identifiers into LiveKit so the agent can recall prior customer context on demand.

The complete setup instructions, Twilio Functions, LiveKit agent code, and SIP configuration templates are in the GitHub repository. Use this page as the architecture walkthrough and the repo README as the implementation guide.

Pattern A

Using Studio

Studio owns the journey, redirects to LiveKit, then resumes and chooses the next route when the AI escalates.

Pattern B

Using TaskRouter

Twilio calls /voice directly. On escalation, /escalate updates the parent call with <Enqueue>.

Pattern C

Direct TwiML route

Twilio updates the parent call with <Dial>, <Conference>, <Sip>, or a custom <Redirect>.

Conversation Memory is optional and sits on top of Pattern A, Pattern B, or Pattern C. Choose the base handoff pattern first, then add Memory when the agent should recall prior customer context or pass Memory identifiers onward during escalation.

Runtime Flow

How the call moves from AI back to routing

The key design choice is to update the original inbound Twilio call resource during escalation. The LiveKit SIP leg is only the media bridge to the AI agent; it is not the call leg that should be routed to the next destination.

Pattern A

Using Studio

The Twilio number starts a Studio Flow. Studio's redirect_to_livekit TwiML Redirect widget calls /studio_voice, which dials LiveKit over SIP and passes X-Parent-CallSid.

When the LiveKit agent escalates, it posts to /studio_escalate. That Function updates the parent call with a <Redirect> back to the Studio Flow webhook using FlowEvent=return. Studio then follows the widget's return transition into the configured Studio route.

Pattern B

Using TaskRouter

The Twilio number invokes /voice directly. /voice returns <Dial><Sip> with LiveKit SIP authentication and the parent call header.

When the LiveKit agent escalates, it posts to /escalate. That Function updates the parent call with <Enqueue workflowSid="WW..."> and embeds the handoff summary as TaskRouter task attributes.

Pattern C

Direct TwiML route

The LiveKit mechanics stay the same: the agent posts the parent call SID and summary to Twilio when it escalates.

The handoff Function then updates the parent call with another TwiML instruction, such as <Dial>, <Conference>, <Sip>, or <Redirect> to a custom voice app.

Optional Memory keeps the same parent-call handoff. The Memory entrypoint gets context into LiveKit for recall, while the Memory-aware escalation endpoint decides how that context reaches Studio, TaskRouter, or a custom TwiML destination.

Optional Conversation Memory

Add customer memory after choosing the handoff pattern

Memory is an overlay on the baseline call handoff. It adds recall while the caller is with LiveKit, and it can pass Memory identifiers to the next destination when the agent escalates.

1. Configure Memory values

Add MEMORY_STORE_ID and Twilio credentials to the Function environment, then redeploy. The Memory Functions add /voice_memory, /studio_voice_memory, /escalate_memory, /studio_escalate_memory, and /memory_recall. Use /memory_debug for protected live diagnostics.

2. Switch the LiveKit entrypoint

Pattern A swaps the Studio TwiML Redirect URL from /studio_voice to /studio_voice_memory. Pattern B points the Twilio number to /voice_memory. Pattern C uses whichever Memory entrypoint matches its base route.

3. Add the Memory agent tool

Use examples/livekit_agent_tool_memory.py when the agent should expose recall_customer_memory. The tool calls /memory_recall only when prior context would help the conversation.

4. Map the Memory SIP headers

Add X-Customer-Phone, X-Memory-Store-Id, and X-Memory-Profile-Id to the LiveKit trunk's header-to-attribute mapping. If the profile is not found before dialing, /memory_recall can resolve it later from the caller phone and Memory Store ID.

5. Verify the lookup path

If the agent cannot find prior context, POST to /memory_debug with customerPhone and the optional Conversation Orchestrator configuration ID. Check that the store is active, the profile is found, the config uses the same store, and Memory extraction is enabled.

Pattern A

/studio_escalate_memory

Redirects the parent call back to Studio with the summary and Memory identifiers, so Send to Flex or another widget can use them.

Pattern B

/escalate_memory

Updates the parent call with <Enqueue> and includes the summary and Memory identifiers in TaskRouter task attributes.

Pattern C

Custom endpoint

Updates the parent call with your chosen TwiML. If the destination is not Studio or TaskRouter, store or forward the summary and Memory identifiers through a context channel that destination can read.

Memory lookup is best-effort. If the lookup fails or the profile is not available before dialing LiveKit, the caller still reaches the agent through the normal parent-call handoff.

Parent Call Update

The small detail that makes the handoff work

Twilio creates a parent call leg for the original inbound caller and a child SIP leg for LiveKit. The handoff must update the parent leg.

Header passed to LiveKit

const parentCallSid = event.CallSid;
const sipParams = new URLSearchParams({
  "X-Parent-CallSid": parentCallSid,
  "X-Handoff-Id": event.CallSid,
});

Pattern A: Studio return

<Redirect method="POST">
  .../Flows/FW...?FlowEvent=return
</Redirect>

Pattern B: TaskRouter Enqueue

await client.calls(parentCallSid).update({
  twiml: enqueueTwiml.toString(),
});

Avoid updating the SIP child leg exposed inside LiveKit. That leg represents the AI media bridge. The parent call is the live caller that needs to be moved to the next route. Pattern C uses this same update but swaps in another TwiML verb, such as <Dial> or <Conference>.

Task Attributes

Context passed into TaskRouter

The escalation Function serializes handoff context into the TaskRouter task. Flex can read these attributes from the active reservation or task, and another TaskRouter-powered agent experience can consume the same attributes. Memory fields are optional additions. 

{
  "direction": "inbound",
  "channelType": "voice",
  "reason": "ai_escalation",
  "name": "LiveKit AI escalation",
  "parentCallSid": "CA...",
  "handoffId": "CA...",
  "intent": "account_access",
  "summary": "Caller tried a new sign-in code and still needs help.",
  "description": "Caller tried a new sign-in code and still needs help."
}

With Conversation Memory enabled, add optional attributes such as customerPhone, memoryStoreId, and memoryProfileId so Flex or another TaskRouter consumer can display or use the context. 

{
  "customerPhone": "+15551234567",
  "memoryStoreId": "mem_store_...",
  "memoryProfileId": "mem_profile_..."
}

Setup Checklist

Build it in six moves

1. Deploy Twilio Functions

Deploy /studio_voice, /studio_escalate, /voice, and /escalate with the LiveKit SIP host, SIP credentials, shared handoff token, and whichever routing values your chosen pattern needs. Add the Memory endpoints only when enabling the optional Memory overlay.

2. Create LiveKit SIP resources

Create the inbound trunk from the template, then bind the SIP dispatch rule to the returned ST... trunk ID. The baseline mapping needs parentCallSid and handoffId; Memory adds customer and profile attributes.

3. Choose number routing

For Pattern A, point the Twilio number to the Studio Flow webhook. For Pattern B, point it directly at the public /voice Function URL. For Pattern C, start from either route and change the handoff TwiML destination.

4. Configure the destination

For Pattern A, import or create the Studio Flow. For Pattern B, use a TaskRouter Workflow SID. For Pattern C, decide whether the parent call should dial, conference, SIP, or redirect elsewhere.

5. Add the LiveKit tool

Add the handoff tool to the LiveKit agent. Use /studio_escalate for Pattern A, or /escalate for Pattern B and Pattern C style adaptations. For Memory, use the Memory-enabled agent example and choose the Memory escalation endpoint for the destination.

6. Test the parent call update

Confirm LiveKit receives parentCallSid, the tool posts that value back to Twilio, and the original caller leg follows the selected route with the expected handoff context.
