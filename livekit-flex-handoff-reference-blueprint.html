Reference Blueprint

Twilio LiveKit Call Handoff

A production-shaped pattern for giving a LiveKit voice agent a clean escape hatch back to Twilio routing, without losing the live caller or the context gathered by the AI.

View Call Flow Implementation Map Open GitHub Repo
Patterns: Studio, Enqueue, or custom TwiML Voice + LiveKit + routing

What This Blueprint Solves

AI containment with a safe parent-call handoff

The integration lets a LiveKit voice agent handle the first part of an inbound support call. When the agent cannot resolve the issue, it calls a tool that updates the original Twilio call. Flex is the tested reference destination, but the same pattern can route the live caller to another TaskRouter workflow, voice app, SIP endpoint, conference, or dial target.

The complete setup instructions, Twilio Functions, LiveKit agent code, and SIP configuration templates are in the GitHub repository. Use this page as the architecture walkthrough and the repo README as the implementation guide.

Pattern A

Studio return to Flex

Studio owns the voice journey, redirects the caller to LiveKit, then resumes and runs Send to Flex when the AI escalates.

Pattern B

Direct Enqueue to Flex

The Twilio number calls /voice directly, then /escalate updates the parent call with <Enqueue>.

Pattern C

Direct TwiML route

The same parent call update can dial another destination, enter a conference, reach a SIP endpoint, or redirect to a custom voice app.

Runtime Flow

How the call moves from AI back to routing

The key design choice is to update the original inbound Twilio call resource during escalation. The LiveKit SIP leg is only the media bridge to the AI agent; it is not the call leg that should be routed to the next destination.

Pattern A

Studio return to Flex

The Twilio number starts a Studio Flow. Studio's redirect_to_livekit TwiML Redirect widget calls /studio_voice, which dials LiveKit over SIP and passes X-Parent-CallSid.

When the LiveKit agent escalates, it posts to /studio_escalate. That Function updates the parent call with a <Redirect> back to the Studio Flow webhook using FlowEvent=return. Studio then follows the widget's return transition into Send to Flex.

Pattern B

Direct Enqueue to Flex

The Twilio number invokes /voice directly. /voice returns <Dial><Sip> with LiveKit SIP authentication and the parent call header.

When the LiveKit agent escalates, it posts to /escalate. That Function updates the parent call with <Enqueue workflowSid="WW..."> and embeds the handoff summary as TaskRouter attributes.

Pattern C

Direct TwiML route

The LiveKit mechanics stay the same: the agent posts the parent call SID and summary to Twilio when it escalates.

The handoff Function then updates the parent call with another TwiML instruction, such as <Dial>, <Conference>, <Sip>, or <Redirect> to a custom voice app.

Parent Call Update

The small detail that makes the handoff work

Twilio creates a parent call leg for the original inbound caller and a child SIP leg for LiveKit. The handoff must update the parent leg.

Header passed to LiveKit

const parentCallSid = event.CallSid;
const sipParams = new URLSearchParams({
  "X-Parent-CallSid": parentCallSid,
  "X-Handoff-Id": event.CallSid,
});

Pattern A: return to Studio

<Redirect method="POST">
  .../Flows/FW...?FlowEvent=return
</Redirect>

Pattern B: direct Enqueue

await client.calls(parentCallSid).update({
  twiml: enqueueTwiml.toString(),
});

Avoid updating the SIP child leg exposed inside LiveKit. That leg represents the AI media bridge. The parent call is the live caller that needs to be moved to the next route. Pattern C uses this same update but swaps in another TwiML verb, such as <Dial> or <Conference>.

Task Attributes

Context passed into Flex

The escalation Function serializes handoff context into the TaskRouter task. Flex can read these attributes from the active reservation or task. 

{
  "direction": "inbound",
  "channelType": "voice",
  "reason": "ai_escalation",
  "name": "LiveKit AI escalation",
  "parentCallSid": "CA...",
  "handoffId": "CA...",
  "intent": "account_access",
  "summary": "Caller tried a new sign-in code and still needs help.",
  "description": "Caller tried a new sign-in code and still needs help."
}

Setup Checklist

Build it in six moves

1. Deploy Twilio Functions

Deploy /studio_voice, /studio_escalate, /voice, and /escalate with the LiveKit SIP host, SIP credentials, shared handoff token, and whichever routing values your chosen pattern needs.

2. Create LiveKit SIP resources

Create the inbound trunk from the template, then bind the SIP dispatch rule to the returned ST... trunk ID.

3. Choose number routing

For Pattern A, point the Twilio number to the Studio Flow webhook. For Pattern B, point it directly at the public /voice Function URL. For Pattern C, start from either route and change the handoff TwiML destination.

4. Configure the destination

For Pattern A, import or create the Studio Flow and configure Send to Flex. For Pattern B, use a Flex Workflow SID. For Pattern C, decide whether the parent call should dial, conference, SIP, or redirect elsewhere.

5. Add the LiveKit tool

Add the handoff tool to the LiveKit agent. Use /studio_escalate for Pattern A, or /escalate for Pattern B and Pattern C style adaptations.

6. Test the parent call update

Confirm LiveKit receives parentCallSid, the tool posts that value back to Twilio, and the original caller leg follows the selected route with the expected handoff context.

Adaptation

Pattern C: route without Flex

Flex is the concrete tested target in this blueprint, not a requirement of the parent-call update pattern. If your agent stack uses TaskRouter, enqueue the parent call and pass context as task attributes. If it does not, route the live call with TwiML such as <Dial>, <Conference>, or <Redirect>, and provide the handoff summary to the receiving system through a separate context channel.
